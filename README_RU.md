## Покрытие тестами

**Positive E2E:** получение гостевого OAuth-токена → добавление товара → получение корзины → изменение количества → проверка изменений → добавление второго товара → проверка обоих товаров → удаление второго товара → проверка удаления → удаление оставшегося товара → проверка пустой корзины. Проверяются HTTP-статусы, идентификаторы, SKU, количество, `itemCount`, доступность товаров, валюта (когда поле присутствует), отсутствие ошибок.

**Negative Tests:** корзина без авторизации (`401`), неверный Bearer Token (`401`), некорректный SKU (`422`), проверка отсутствия некорректного SKU в корзине (`200`), отсутствие обязательного заголовка `aeSite` (`400`), недопустимое количество товара (`400`).

**Utilities:** GET-запрос проверяет доступность сохранённого токена и успешный ответ API корзины. Общий скрипт перед запросами умеет обновлять отсутствующий/просроченный Guest Token; отдельный тест Utilities не является исчерпывающей проверкой механизма истечения срока действия токена.

## Подготовка

1. Установите **Postman Desktop** и импортируйте `postman/American_Eagle.postman_collection.json` (формат Collection v2.1).
2. Получите **правомерно предоставленные** Basic-учётные данные для гостевого OAuth API. Не используйте чужие данные и не сохраняйте их в Git.
3. В **Postman Vault** создайте локальный секрет `ae_basic_auth` со значением полного заголовка `Basic <учётные_данные_в_base64>`. Если Postman запросит разрешение на использование Vault из скриптов, разрешите его только для доверенной коллекции. Секрет **не экспортируется** вместе с JSON.
4. Проверьте редактируемые значения `skuId` и `skuId2`: оба SKU должны быть актуальными, доступными и различными. Переменные `quantity=1` и `updatedQuantity=2` также можно менять. `token`, `cartId`, `itemId` и `itemId2` в экспортированном файле пустые, значения формируются при выполнении.
5. Если требуется прокси, настройте его в Postman. Региональные ограничения и антибот-защита стороннего сайта могут влиять на результат.

## Запуск

В меню коллекции выберите **Run**, оставьте **все 18 запросов в существующем порядке**, установите **1 итерацию** и при необходимости задержку **500 мс** между запросами. Можно запускать папки отдельно: **Positive E2E**, **Negative Tests**, **Utilities**. Проверка отсутствия неверного SKU предполагает пустую корзину, поэтому предпочтителен полный последовательный запуск.

Запрос `Get Guest Token` и общий `Before request` получают значение `ae_basic_auth` из Postman Vault. После успешной авторизации в переменные коллекции сохраняются `token` и `token_expires_at`; следующие запросы используют `Bearer {{token}}`. Для двух негативных проверок обновление токена пропускается: запросы выполняются без авторизации либо с намеренно неверным токеном.

При `401` проверьте доступ к Vault, данные авторизации и настройки запроса. При неожиданном `400` проверьте обязательные заголовки (`aesite`, `aelang`, `aecountry`) и тело запроса. Для негативного сценария неверного SKU ожидается `422`.

## Безопасность и ограничения

- Не публикуйте Basic-учётные данные, JWT, Cookies, файлы окружений с секретами и сетевые логи с токенами.
- В JSON нет сохранённых значений реальных Bearer/Basic-секретов, но **проверяйте каждый новый экспорт перед коммитом**. Postman Vault хранится локально и не переносится через Git.
- SKU, проверки и формат ответов зависят от стороннего работающего API и могут потребовать обновления.
- Результат получен **локально в Postman**, а не в CI. Соблюдайте правила использования сервиса и не перегружайте API запросами.
